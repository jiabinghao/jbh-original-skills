# 项目上下文核对

定位方案与已有项目事实的冲突，并形成能够追溯的修订建议。默认中文输出；保留项目既有术语和文档格式。

## 建立证据范围

先读取仓库指引和用户指定的材料，再定位需求文档、业务术语、架构决策与相关代码入口。记录分支或提交以及文档日期，避免把不同版本混成一个结论。没有代码时只评审所给文档，不声称实现已核验。

针对这次变更列出受影响的行为与不变量，例如权限判定、金额单位、对象生命周期和数据归属。对每个重要判断找到可复查的文件位置或原始来源。

## 处理不一致

区分术语不同、业务规则冲突、文档过期和真正缺少决策。代码说明当前行为，文档说明已记录的意图，两者冲突时不能默认为任一方正确。用具体场景展示冲突后果，如“已取消订单是否仍能退款”，避免只批评抽象一致性。

可以在上下文确定的情况下统一表述；涉及业务选择时提出精确问题，同时完成其他不依赖答案的核对。不要借机创建新的项目文档体系。

## 形成修订

按用户范围更新已有文档，或提供清晰补丁。决策记录应包含触发原因、所选行为、主要代价、受影响位置和将来重新评估的条件。未确定的选择标成待决，不伪造用户或团队批准。

交付按影响排序的冲突清单、修订后的行为说明和验证范围。如果只完成文档修订，明确代码还未修改；如果已经实施，则给出实际检查结果。所有引用应能让接手者直接找到证据。
