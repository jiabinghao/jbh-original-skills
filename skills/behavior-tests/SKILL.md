# 行为驱动的测试先行

用测试证明用户关心的行为。默认中文说明，沿用项目现有测试框架。

## 选择有效测试点

把需求改写成输入、动作和可观察结果，优先覆盖实际风险及关键边界。选择公开接口或稳定的业务入口；避免以内部函数名、调用次数或代码排布替代用户行为。外部服务在边界处隔离，保留需要验证的业务逻辑。

先运行受影响的已有测试，记录环境问题和预先存在的失败。测试工具不可用时可以编写用例，但必须说明未执行，不伪造通过状态。

## 让失败提供证据

新增一个能区分正确与错误实现的用例并执行。检查失败原因确实来自缺失或错误的行为。语法错误、导入错误和环境故障不算行为失败；先解决或准确记录这些问题。

如果新用例直接通过，检查它是否触达目标路径、断言是否足够以及原实现是否已经满足需求。不要为了形式而人为破坏已有正确行为。

## 实现与整理

实现当前用例所要求的行为，然后运行同一用例。通过后再整理重复代码或命名，保持断言稳定。继续添加最能暴露剩余风险的场景；避免一次堆积大量相似测试。

只有完成下一项测试必须的结构调整才在此范围内进行。更大重构另行说明。对不稳定时间、随机数和网络采用可控输入，并检查测试能独立运行。

## 交付证据

报告测试覆盖的行为、实际执行命令和结果、修复前的失败原因及仍未覆盖的边界。运行受影响测试集和必要的构建检查；若已有无关失败，明确区分。用户要求普通低风险文本修改时不套用此流程。
