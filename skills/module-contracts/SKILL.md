# 模块边界与契约设计

从调用者任务出发设计接口。先查项目已有约定和真实调用方式，找出需要隐藏的变化与必须暴露的业务决策；不通过增加接口层数量来证明设计更好。

## 定义边界

选取正常、失败和重试场景，明确哪个模块持有状态、哪个模块控制流程、哪些副作用由谁执行。变化通常共同发生的逻辑可以放在同一边界；仅因使用同一种技术不必合成一个模块。

检查调用者是否必须理解内部存储、缓存或供应商细节才能完成普通任务。若是，调整契约以隐藏实现机制；业务上的重要限制仍须暴露，不能把不确定行为包装为无条件成功。

## 写出可使用的契约

为必要操作说明输入、输出、前置条件、状态变化、失败分类及资源责任。涉及重复请求时明确是否幂等、标识作用域和有效期；涉及异步工作时区分“已接受”与“已完成”。并发写入需说明冲突如何发现，不默认全局串行。

先写调用示例，验证接口能表达核心任务和恢复路径，再决定内部结构。比较候选时同时考虑调用者复杂度和实现维护成本，避免将简短函数签名误当作简单使用体验。示例只作为设计检验，不把伪实现的成功结果当作运行证明。

## 与项目衔接

需要实现时只完成用户授权的模块与调用点，按项目工具验证契约。现有公开接口变更须说明兼容方式及迁移范围，不能悄悄改变错误语义。仅请求设计时交付接口草案、场景说明、取舍和待决条件。

本技能侧重设计新的边界与契约；已有维护问题驱动的局部重构应按具体问题处理，不强制套用全项目架构改造。
