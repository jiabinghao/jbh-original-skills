# React 性能改进

从用户感受到的慢开始，确定页面、操作、数据量与设备条件。读取依赖及锁文件，确认 React、Next.js 版本和路由方式；普通 React 项目不套用 Next.js 的服务端规则。

## 建立可比较的基线

区分等待网络、JavaScript 执行、React 更新与浏览器布局绘制。记录现有行为和测量条件：开发或生产构建、冷启动或缓存命中、输入规模、设备限制。对同一操作重复观测，报告范围和波动；不能把开发模式的额外执行直接当作生产回归。

可使用项目已有分析工具、浏览器性能面板或 [React Profiler](https://react.dev/reference/react/Profiler)。Profiler 有额外开销，普通生产构建默认不启用，需按版本文档判断测量方式。没有运行工具时只能给出静态疑点，不能编造提速百分比。

## 按瓶颈选择修改

请求等待先画出真实的数据依赖，再考虑让相互独立的请求并行或减少重复请求；有顺序依赖的请求不能强行并行。缓存必须说明对象、作用范围和失效条件，避免跨用户复用私有数据。

渲染问题先核对状态归属、列表标识与重复计算。衍生数据可在渲染中计算，避免用 Effect 制造额外状态同步；需与外部系统同步的 Effect 保留正确依赖，不能通过删依赖隐藏问题。参考 [React 的 Effect 说明](https://react.dev/learn/you-might-not-need-an-effect)。仅在测量支持时引入记忆化，并检查其依赖和维护成本。

客户端体积问题先确认哪些代码确需交互。Next.js 项目根据对应版本的 [服务端与客户端组件文档](https://nextjs.org/docs/app/getting-started/server-and-client-components)核对边界；不要因为减少包体就破坏浏览器 API 使用或数据序列化。按实际加载路径处理重型依赖，不擅自迁移全项目技术栈。

## 验证与交付

修改后重跑同一场景，并检查数据一致性、加载错误和主要交互。交付具体改动、基线与新结果、成本和剩余疑点。指标改善须附测量口径；代码更简洁不自动等于运行更快。
